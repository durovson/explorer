# План миграции с исходного архива на архитектуру GRNT

## Что сохранено из исходного проекта

- прямой заказ без пополнения и внутреннего баланса;
- только TON и официальный USDT в сети TON;
- фиксированная цена заказа, уникальный memo и 15-минутный TTL;
- адаптер покупки Stars/Premium через Fragment API;
- точное сопоставление адреса, актива, суммы и memo.

## Что перенесено из GRNT

- пакетная структура `app/` и явная композиция зависимостей;
- отдельные handlers, services, repositories, models, tasks и API;
- Supabase как источник истины и атомарные PostgreSQL RPC;
- одна media-карточка с заменяемыми GIF/PNG;
- пагинированный список заказов, реферальная атрибуция и админ-статистика;
- независимые фоновые циклы, health endpoint и Render-конфигурация.

## Финансовая машина

`WAITING_PAYMENT → PAYMENT_CONFIRMED → PROCESSING → COMPLETED`

- неоплаченный заказ становится `EXPIRED` или `CANCELLED`;
- доказанный отказ Fragment становится `FAILED`;
- таймаут/5xx/невалидный ответ после отправки становится `MANUAL_REVIEW`;
- автоматического повтора неоднозначной Fragment-попытки нет;
- ручной `/approve_retry UUID причина` оставляет аудит администратора.

## Рефералы без внутреннего баланса

Связь referrer сохраняется один раз. Статистика показывает приглашенных и завершенные
заказы. `referral_rewards` — неизменяемый ledger отдельных прямых выплат, а не
доступный пользователю баланс: в боте нет пополнения, вывода или расходования суммы.
Автоматический исходящий payout намеренно не включен без отдельного безопасного
кошелька и подтвержденного бизнес-правила.

## Порядок запуска

1. Применить `supabase/schema.sql`.
2. Заполнить `.env` по `.env.example`.
3. Проверить реальные Fragment credentials и контракт endpoint-ов поставщика.
4. Добавить GIF в `app/assets/media/` под документированными именами.
5. Запустить тесты, затем один экземпляр Render в polling-режиме либо webhook.
